## 端到端调用流程（以 chat 为例）

```
1. 用户在 chat 输入消息
   packages/views/chat → packages/core/chat/mutations.ts
                       → api.sendChatMessage()  [HTTP POST]

2. Server 收到消息
   handler 写消息入库 → TaskService.EnqueueTaskForChat()
   → 在 agent_task_queue 表插入一行 status=pending
   → WS 广播 chat:message 给前端（pending 渲染）

3. Daemon 轮询 claim
   pollLoop → WS RPC tasks.claim (批量) 或 HTTP /tasks/claim 兜底
   wsRPCClient.Call (wsrpc.go) — 多路复用同一条 WS 控制连接
   server 在 ClaimTasksByRuntime 里把 pending → dispatched，
   附带 Task 全量上下文（issue/agent/skills/repos/auth_token...）

4. Daemon handleTask (daemon.go:3387)
   a. 解析 runtime → AgentEntry (provider/path/model)
   b. 准备执行环境 (execenv/context.go): work_dir/git/skills/MCP 配置
   c. client.StartTask() 通知 server → running
   d. agent.New(provider, cfg).Execute(ctx, prompt, opts)
      └─ spawn 子进程（NDJSON stream-json 协议）
         · openclaw.go   → claude CLI
         · codex.go      → codex CLI
         · hermes.go     → hermes CLI
         · codeany.go    → node runner.mjs (@codeany/open-agent-sdk)
         · qwen.go       → qwen CLI ...
      └─ processOutput 解析每行 JSON → Message{Text/ToolUse/ToolResult}
   e. 子进程退出 → Result{Status, Usage, SessionID, WorkDir}

5. Daemon 回流结果
   reportTerminalTask → client.CompleteTask / FailTask
   server 写回 task 行 + agent 评论/状态变更 + WS 广播

6. Frontend 通过 WS chat:message / task:updated 实时刷新
```

## 三层各自职责

### Frontend（`apps/*` + `packages/*`）
- React Query 管所有 server state，Zustand 管 view state
- 通过 `packages/core/api/client.ts` 走 HTTP，`ws-client.ts` 走 WS
- **不直接接触 runtime**：只跟 server 通信；runtime 列表也是 server 返回的数据
- WS 事件更新 React Query cache，不写 Zustand 镜像数据（AGENTS.md 硬规则）

### Server（`server/cmd/server`）
- 任务队列的**单一真相源**：`agent_task_queue` 表 + `TaskService.EnqueueTask*`
- 多种入队入口：`EnqueueTaskForIssue`（assignee）/ `EnqueueTaskForMention`（@agent 评论）/ `EnqueueTaskForSquadLeader` / `EnqueueTaskForChat` / autopilot / quick-create
- 暴露 claim/complete/start 接口给 daemon（`router.go:815-819`）
- 维护 runtime 注册表：daemon 上报的 runtime 写入 DB，前端按 workspace 可见性查询
- 鉴权、token mint（task-scoped `mat_*` token 注入子进程 `CHIMII_TOKEN`）
- WS 广播 task 状态变化给前端

### Daemon（`server/internal/daemon` + `cmd/multica/cmd_daemon.go`）
- **机器级常驻进程**，每台机器一个；`make daemon` 或 desktop 启动
- 启动时 `detectBuiltinRuntimes` 探测 PATH 中的 CLI（claude/codex/hermes/...）+ 自定义 runtime profile，注册给 server
- `pollLoop` (daemon.go:3066) 批量 claim task → `handleTask` (daemon.go:3387)
- 真正的**runtime 执行器**：
  - `execenv/` 准备 work_dir、git checkout、skill 写入、MCP config 合并（`runtime_mcp.go`）
  - `agent.New(provider)` 选 backend，`backend.Execute()` spawn 子进程
  - 看门狗：`AgentIdleWatchdog`(30min) / `AgentToolWatchdog`(2h) / `AgentTimeout`（无 wall-clock 上限，0=无限）
  - GC：定期清理已完成 issue 的 work_dir / Codex session store
- 与 server 双通道：WS RPC（首选，多路复用）+ HTTP（兜底，避免 WS 不可用时挂死）

## Runtime 这个概念

在 52tuan 里 **runtime = provider + 可执行路径 + 注册到某 daemon**：

| 概念 | 位置 |
|---|---|
| `Runtime` struct | [types.go](file:///Users/chunjun/Desktop/Build/Agent-harness/52tuan/server/internal/daemon/types.go) — daemon 上报 |
| `runtime_profile` 表 | server DB — 自定义 runtime（用户配的 argv 命令） |
| `agent.Config` + Backend | [pkg/agent/agent.go](file:///Users/chunjun/Desktop/Build/Agent-harness/52tuan/server/pkg/agent) — 17 个 provider 实现 |
| 探测注册 | `detectBuiltinRuntimes` / `probeBuiltinRuntime` (daemon.go) |
| MCP 叠加 | [runtime_mcp.go](file:///Users/chunjun/Desktop/Build/Agent-harness/52tuan/server/internal/daemon/runtime_mcp.go) — runtime 级 + agent 级 MCP 合并 |

Frontend 永远只见 server；Server 只调度不执行；Daemon 才是 runtime 的真正宿主。这是 52tuan 区别于"server 内嵌 agent loop"架构的核心设计——把执行节点放在用户机器/沙箱里，让本地凭据、文件系统、git 操作直接由 daemon 负责。
